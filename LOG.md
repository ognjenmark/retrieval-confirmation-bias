## 2026-11-05

**Run.** The first full-corpus BM25 run (notebook section 4) was stopped by Claude Code because the system was low on memory; no corpus index and no corpus result exist yet.

**Decided.** The rerun happens overnight with a memory limit. `CLAUDE.md` now says that a gold document contains the final answer, and that refuting a wrong candidate is our inference, to be checked with manual labels.

**Rerun.** `scripts/build_corpus_index.py` built the full-corpus index under a 14 GB limit (peak reported by the script: 8.46 GB) and the notebook ran through section 4. BM25 with q0 on development questions is well above random over the full corpus, with low absolute recall; the numbers are in the notebook output and `results/bm25_q0_corpus_dev.csv`. So the chance-level result is specific to the pools. Pool diagnostics are saved in `results/bm25_pool_diagnostics_dev.csv`. Low recall at small k may still limit how well a drop can be measured there.

**Keyword query.** Added q_keywords, the question's terms rarest in the corpus: N = 20 fixed in advance, N = 10 and 40 as sensitivity only (notebook section 5, `results/bm25_keywords_pool_dev.csv`, `results/bm25_keywords_corpus_dev.csv`). On development questions it retrieves gold documents better than q0 at N = 20 in both spaces, so comparing candidate queries with q0 would mix in the gain from shortening; they will be compared with q_keywords. N stays 20 even where 10 scores higher. A first notebook run failed with `MemoryError` under `ulimit -v 14000000`, although enough memory was free and the same code had passed before; the cause was not confirmed. Runs now use `systemd-run --user --scope -p MemoryMax=14G -p MemorySwapMax=0`, which limits real memory. Intervals are not corrected for multiple comparisons.

**q_true.** Added q_true, q_keywords plus the correct answer (notebook section 6, `results/bm25_q_true_*_dev.csv`, `results/mention_q_true_*_dev.csv`, `results/answer_stats_dev.csv`). On development questions it raises gold retrieval strongly in both spaces. The string match for mentions misses part of the gold documents, so mention counts do not equal gold labels. The corpus cannot fully remove the construction concern: gold documents were found with the answer known, in the pools and in the corpus alike. H1, H2 and H4 are not tested yet, because no wrong candidate has been run.

**q_random.** Added q_random, q_keywords plus the answer of another development question of the same rule-based type (date, number, other), rejected if it overlaps the correct answer or appears in a gold document (notebook section 7, `results/bm25_q_random_*_dev.csv`, `results/mention_q_random_*_dev.csv`, `results/candidate_stats_q_random_dev.csv`; candidates only in `data/browsecomp-plus/q_random_dev.jsonl`). On development questions recall changes little in either space, and the mean first gold rank in the corpus gets worse. Nearly all pools do not contain the candidate as a string, so pools cannot measure candidate echo for this query. In the corpus, candidate mentions in the top 10 rise, and gold documents of the question the candidate came from appear there, so part of the rise may come from how the corpus was built. This is a control with one draw per question; it does not test H1. Intervals are not corrected for multiple comparisons.
